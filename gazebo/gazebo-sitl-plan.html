Draganfly · simulation_environment · feasibility & implementation plan

Headless Gazebo, two cameras

Replacing the synthetic demo cameras with a headless Gazebo world driving ArduPilot SITL, streaming through GstCameraPlugin — so test flights have something real to navigate by.

Status Working end-to-end on sim1 — registry image pending first gazebo-v* tag Target host Windows 11 · Docker Desktop Verdict GO, at a revised frame rate

Feasible — and one constraint makes it comfortably so

Gazebo can drive SITL and deliver camera views into the existing RTSP path. Two things shape the design. First, “replace the demo_video_source containers” is really “re-source the pixels”: those containers also speak the entire MAVLink camera protocol, and GstCameraPlugin speaks none of it. The MAVLink half has to survive, or QGC and DGCS lose camera discovery.

Second — and decisively — only one stream is ever watched at a time, and selection happens when the client connects to an RTSP path. That turns the hardest constraint into the cheapest design: MediaMTX already fires hooks on reader connect and disconnect, so a camera renders only while someone is actually watching it. Peak render load is one camera, not two, and an idle rig costs nothing but physics.

P0 — measured

What this box actually does

Measured on the real image (Gazebo Harmonic, llvmpipe software rendering) with ArduPilot SITL connected over the JSON FDM link. Real-time factor is the number that matters: below 1.0 the physics clock falls behind and the autopilot starts seeing late FDM frames.

ConfigurationRTFCamera FPSGazebo CPUVerdict
Physics only, no cameras 1.00—1.3 cores Real time
One camera, 1280×720 0.92–0.95205.9 cores Usable
Two cameras, 1280×720 0.447.8 each5.0 cores Fails

Three conclusions. One camera at 720p is viable, but delivers 20fps, not 30 — the locked target is missed and needs revising to 720p20 (or 720p15 with margin). Two cameras are not merely slower, they are disqualifying: RTF 0.44 means the vehicle flies against a physics clock running at 44% of real time. And note the two-camera row uses less CPU than the one-camera row while performing far worse — rendering serialises per step, so the second camera doubles frame time rather than consuming another core.

The consequence is the important part: the render gate is load-bearing, not an optimisation. Without it the rig cannot host two cameras at all. That inverts the earlier reading of this risk.

Two things also passed ahead of schedule: the JSON FDM link came up unaided (JSON control interface set to …:9002, JSON received:), which is P1's core mechanism; and --headless-rendering initialised Ogre2 through EGL with no X server, as designed.

The demo cams do two jobs

demo_video_source.py generates video and implements the camera protocol as component 103/104. Only the first job moves to Gazebo; the second must be kept.

Bridge required

The plugin emits bare RTP

GstCameraPlugin streams RTP/UDP H.264 to a host and port — it does not publish RTSP, and MediaMTX cannot ingest bare RTP without an SDP. A thin receiver republishes it.

Halves the load

One viewer, one camera

Streams are never watched in parallel, and the client selects by connecting to a path. MediaMTX's on-demand hooks turn that into a render gate, so the peak cost is a single camera.

2 · The camera shim gains three flags

Only ffmpeg's input stage changes. Because Gazebo already delivers H.264, the bridge copies the stream rather than re-encoding it — the largest CPU saving available on this box.

# --video-source test (today, unchanged)
ffmpeg -re -f lavfi -i testsrc=... -c:v libx264 ... -f rtsp $RTSP_URI

# --video-source rtp (new)
ffmpeg -protocol_whitelist file,udp,rtp -i /tmp/gz_cam1.sdp \
       -c:v copy -f rtsp $RTSP_URI

# identity, so the operator can tell the views apart
--camera-vendor DRAGANFLY --camera-model "DF SIM FORWARD"   # gzcam1
--camera-vendor DRAGANFLY --camera-model "DF SIM DOWN"      # gzcam2

3 · Render only while watched

As built (the original MTX_PATHS_*_RUNONDEMAND hooks cannot work — see B2): camera_gate.py runs alongside gz sim in the gazebo container, polls MediaMTX's read-only API for each path's reader count, and drives the camera's enable topic through a persistent gz-transport publisher, re-publishing desired state every tick.

mediaserver:
  environment:
    MTX_API: "yes"                                  # read-only HTTP API on :9997
    MTX_AUTHINTERNALUSERS_1_IPS: 172.28.0.0/16      # let the sim subnet query it

gazebo:                                             # camera_gate.py, every 2s:
  GET /v3/paths/get/cam1  -> readers > 0  -> /cam1/enable = true   (immediately)
                          -> readers == 0 -> /cam1/enable = false  (after 10s hold)

nobody connected  -> no camera renders, physics only
one reader        -> exactly one camera renders

Risk

What could go wrong

#RiskSeverityMitigation
R1 Software rendering cannot hold 720p30 even for a single camera. Confirmed Materialised, partially. P0 measured 20fps at 720p for one camera, not 30 — resolution holds, frame rate does not. Revise the target to 720p20, or 720p15 for margin. Not fatal: 20fps is usable for navigation.
R2 The WSL d3d12 accelerated path may not expose /dev/dxg usefully to Docker Desktop containers on an AMD iGPU. Medium Treated as upside, not baseline. The plan assumes llvmpipe; d3d12 is tested in P0 and adopted only if it wins.
R3 H.264 caps from the plugin may not survive -c:v copy into MediaMTX, forcing a re-encode. Medium Verified in P2 with a static SDP. If passthrough fails, fall back to re-encode and re-check the budget against P0.
R4 Slow rendering starves the physics step, so SITL sees late FDM frames and flight behaviour degrades. Confirmed Real and measured. Two cameras drop RTF to 0.44; one camera holds 0.92–0.95; no cameras 1.00. Rendering does gate the FDM loop. The only mitigation that works is keeping exactly one camera rendering — which makes the render gate mandatory, not optional.
R5 On-demand start latency: enabling the sensor, waiting for a keyframe and publishing could leave the first seconds after connect blank, or trip a client timeout. Medium Materialised, twice, and fixed. The reader that triggers the placeholder→RTP switch is dropped by that switch, and the RTP publisher takes ~4–5s to come up (measured via mediamtx's session log) — reverting on a single zero-reader poll made the switch impossible and the stream flapped forever. Fixed with two symmetric holds: the camera gate keeps a camera enabled for 10s of continuous zero readers (GZ_CAMERA_GATE_DISABLE_HOLD), and the bridge holds RTP mode for 10s of zero readers before reverting (GZ_CAM_RTP_REVERT_HOLD). A reconnecting viewer converges to the real 720p stream in ~10s and holds indefinitely.
R6 New 2–4 GB image is a slow first pull and a new artifact to maintain. Low Pinned tag, layer-ordered Dockerfile, CI build on tag. Only the gazebo profile pulls it; demo users never do.
R7 New ports (9002/9003, 5600/5601) collide when running side-by-side instances. Low Parameterised from the start. None are published to the host, so collisions only matter inside a shared network. Multi-instance stays unverified until someone needs it.

One risk that is absent: the RTP hop from Gazebo to the bridge never crosses the Docker Desktop host boundary, so the documented host↔container UDP flakiness does not apply to it. Container-to-container UDP on the sim network is reliable.

Blockers — all resolved

What stood between here and P3

Both blockers materialised as predicted — and each needed a second iteration after its first fix failed against the live stack. The details live in gazebo/README.md (“Resolved the hard way”); the short version:

  • B1 — resolved, on the second attempt. The patch makes the plugin's image-topic subscription follow the enable state, so a disabled camera has zero subscribers and gz-sensors skips its render. The first version toggled the subscription inside the enable-topic callback; re-entering gz-transport from its own callback thread intermittently wedged message dispatch, and enables/disables were lost for minutes under reader-driven flapping. v2 records desired state in the callback and reconciles on the simulation thread in PreUpdate() — idempotent, so the gate re-publishes state every tick and any lost message heals within one.
  • B2 — resolved as designed, plus one discovery. The inverted trigger works: camera_gate.py polls MediaMTX's :9997 API from the gazebo container and toggles the cameras itself. The discovery: one-shot gz topic -p publishes are droppable (each spawn re-races publisher discovery), so the gate holds persistent gz.transport13 python publishers instead — measured end of the lost-message failures.
  • Still open — the d3d12 path. d3d12_dri.so is present in the image, so the accelerated route exists but is untested. It remains the one lever that could restore 30fps, or make two simultaneous cameras viable at all.

Verified working end-to-end against the running sim1 stack: SITL flies on Gazebo physics over the JSON FDM link; a reconnecting RTSP viewer on /cam1 or /cam2 converges to the real 1280×720 stream in ~10s and holds; RTF 0.9–1.0 with one camera rendering, 1.0 idle; both cameras disable within ~10–20s of the last reader leaving. Remaining: push the image on the first gazebo-v* tag (P4).
